# Slime Tech Compat：問題台帳と確認手順

## この台帳の読み方

対象は `slime_tech-0.1.44.jar`、SHA-256 `f8ea80558f7f229314fa026311c194aa956f773bc235a76d7598b0a26d3030bb` です。

「確認」は、実ゲームでの再現、静的解析、モデル試験で意味が異なります。本台帳はそれを区別します。

| 記号 | 意味 |
|---|---|
| U | ユーザーの実ゲーム報告。原因の断定ではない |
| S-J | 引継ぎ整理時に対象元JARのリソース／逆アセンブルで確認した部分 |
| S-P | 参考0.3.0のソース・設定・文書で確認した部分 |
| M | 参考0.3.0に同梱されたモデル試験の記録。今回の引継ぎ作成時には再実行していない |
| H | 過去会話の解析報告。今回その結論全体の再確認はしていない |
| I | 静的な処理からの推論。実際の到達条件を含む再現試験が必要 |

P0はリリースの阻害要因／資源整合性の優先調査、P1は通常操作の不具合・重要な説明、P2は運用・互換性・性能、P3は仕様確認・任意改善です。バランス設定や分かりにくい機能が、そのままバグという意味ではありません。

以下の「0.3.0で対応あり」は、すべて**候補実装あり・実機未検証**を意味します。

## BUILD-001：参考0.3.0のビルドと検証が実環境に到達していない

- **優先度／根拠**：P0、S-P・M。
- **事実**：既存配布JARは独立APIスタブでコンパイル。`OfflineWeaver` は独自の注入モデルでありSponge Mixinではない。実依存物によるGradleビルド、ゲーム・専用サーバー起動、JEI画面表示は未実施。Gradle wrapperもない。
- **箇所**：参考ZIP内 `README.md`、`docs/VERIFICATION.md`、`docs/verification.json`、`build.gradle`、`tools/offline_verify.py`、`tools/OfflineWeaver.java`。
- **作業**：本物の依存物でビルドし、本物のMixinを適用する。実際のランタイム・JAR・注入ログで成立を確認する。Java 25の設定とMixinの `JAVA_21` 指定が実ランタイムにどう解釈されるかも確認する。文字列だけ機械的に変更しない。
- **合格条件**：wrapperによるclean buildが成功し、専用サーバーがJEIなしで起動。注入の不足・二重適用・ABIエラーがない。モデル試験と実統合試験を別々に記録する。

## ST-001：採掘用タグ欠落

- **優先度／根拠**：P1、U・S-J・S-P。
- **観測**：ユーザーはCasting Moldに鉄ピッケルを使っても「びくともしない」と報告。原因候補は、適正ツール要求と採掘タグの不整合。
- **静的事実**：対象JARに `data/minecraft/tags/block/mineable/pickaxe.json` がない。参考0.3.0は以下9 IDを追加している。別用途の `data/c/tags/blocks/glass_blocks.json` は存在するため、「すべてのblock tagがない」という説明は使わない。

```text
slime_tech:casting_mold
slime_tech:generator
slime_tech:grinder
slime_tech:destructor
slime_tech:mixer
slime_tech:pump
slime_tech:energy_converter
slime_tech:energy_cell
slime_tech:reactor_core
```

- **箇所**：元JARの `SlimeTech` のブロック登録、各ブロックのloot table。パッチの `src/main/resources/data/minecraft/tags/block/mineable/pickaxe.json`。
- **方針**：元のloot tableと適正ツール設定を再確認し、`replace:false` で不足タグを追加する。必要Tierは根拠のある既存仕様に合わせ、便宜的に鉄以上へ引き上げない。
- **合格条件**：サバイバルで空の対象9機械をツルハシ回収でき、ドロップが二重にならない。不適正ツール・必要Tier・内容入り時の保持仕様は別項目で記録する。

## ST-002：Casting MoldのGel Ingot工程がJEIから追えない

- **優先度／根拠**：P1、U・S-P・H。
- **観測**：Gel IngotのR検索が無反応。Gel Plateからも材料の取得経路が分からなかった。
- **既存解析の結論**：`CastingMoldBlockEntity` にCondensed Slime 1,000 mB → Gel Ingot 1個、200 tick冷却の処理があり、一般recipe JSONだけでは表現されていない。「製法自体が欠落」とした以前の説明は撤回済み。
- **箇所**：元JARの `blockentity.CastingMoldBlockEntity`。パッチの `jei/CastingMoldRecipeCategory.java`、`SlimeTechCompatJeiPlugin.java`。
- **0.3.0**：表示専用カテゴリと機械の関連付けあり。
- **合格条件**：実JEIでGel IngotのR、Casting MoldのU、Condensed Slimeからの用途検索が動く。必要量・時間・出力が元実装と一致し、サーバーレシピ追加や自動転送の誤誘導がない。

## ST-003：初回Gel Ingotの導線・かまどの特殊処理・耐熱配管

- **優先度／根拠**：P1、U・S-J・S-P・H。
- **静的事実**：`FurnaceCondensedSlimeCompat.processFurnaceOutput` はかまどの出力スロット2のDried Slimeを扱う。燃料スロット1に空バケツが**ちょうど1個**ある分岐ではCondensed Slime Bucketへ置換し、残りは座標別SavedDataへ1個あたり1,000 mBとして挿入する。
- **重要な補足**：同クラスに `onServerTick` → `processChunk` の呼出経路もある。「パイプが接続されたときだけ変換される」という過去の説明は前提にせず、実際のタイミングを確認する。
- **既存解析の報告**：Basic Fluid Pipeは高温流体を拒否し、Condensed SlimeにはReinforced Fluid Pipeが必要。後者の製作にGel Ingotが必要なため、初回はバケツ経路を使う。温度判定とレシピも対象JARで再確認する。
- **0.3.0**：JEI情報ページあり。元のゲーム処理は未変更。
- **作業**：Slime Blockを焼く開始状態から、空バケツを置くタイミング、隠し流体に入った後の状態、Casting Moldへの注入まで実演できる手順を作る。既に隠しバッファへ変わった後にバケツを置くだけで戻せるとは書かない。
- **合格条件**：Gel Ingot未所持のサバイバルで最初の1個へ到達できる。JEIだけで手順と耐熱制約が分かる。Slime Quests側の導線は当該JAR未確認のまま断定しない。

## ST-004：Fluid Tankの異種流体合算・誤変換

- **優先度／根拠**：P0、S-P・M・H。元JARの対象クラス・フィールドも存在確認済み。
- **既存解析・モデル記録**：隣接Tank群の量を合算する一方、種類は最初の非空Tankから選ぶ。抽出時の各Tankの種類確認が足りず、水＋溶岩等を一種類として取り出し得る。
- **箇所**：`FluidTankBlockEntity.getNetworkState`、`extractFluid`、`insertFluid`、`refreshNetworkData`、`localAmount`、`storedFluidId`。
- **0.3.0**：`TankSafety` が連結群の生データを検査し、混在・不明ID・不正量・探索上限・未ロード隣接チャンクで停止する。公開集計値は0になり得るが、保存量を消去する意図はない。
- **再現**：水と溶岩を別々に充填し、直接連結／空Tankで橋渡しする。配管、バケツ、GUI、RS External Storageの各経路から操作する。
- **合格条件**：種類別の総量が保存される。停止後の保存再読込でも内容を保持。simulation/transaction rollbackで変更しない。同種接続は正常に使え、混在解消後は復帰する。0表示と空の誤認を減らす診断も整える。

## ST-005：Pumpの動的流体番号だけを保存

- **優先度／根拠**：P0、S-P・M・H。
- **既存解析・モデル記録**：未知のMOD流体にセッション内の1000以降の番号を割り当て、Pumpはその番号だけ保存する。次回起動で登録順が変わると同番号が別流体を指し得る。固定番号1〜4は水・溶岩・Slime Tech固有2流体。
- **箇所**：`PumpBlockEntity.loadMachineData/saveMachineData`、`SlimeTechFluidType`。
- **0.3.0**：レジストリIDを追加保存し、次回ロードで番号を解決。元の流体名がない旧動的番号は推測せず保留する。
- **再現**：流体A/Bの番号割当順を変える。旧形式、0.3.0形式、存在しない流体ID、欠損MOD復旧、空バッファ、不正量を試す。
- **合格条件**：保存後も種類・量・電力が保持される。不明旧データは保留され、2回以上の保存再読込でも診断情報が失われない。流体提供MODが戻った場合の再解決を確認する。

## ST-006：Pumpの流体源消失・変更でバッファ種類が壊れる

- **優先度／根拠**：P0、S-P・M・H。
- **既存モデル記録**：残量があるのに流体源撤去で種類2→0、溶岩源を水源へ変更すると種類2→1になる比較が記録されている。

- **合格条件**：流体源撤去・再設置・種類変更・チャンクアンロードを挟んでも残量の種類が変わらない。異種を追加生成せず、旧バッファが空になった後は正しく新種へ切り替えられる。

## ST-007：Pumpの流体源を消費しない汲み上げ

- **優先度／根拠**：P2・任意ポリシー、S-P・M・H。
- **既存解析の報告**：10 FEで100 mBを追加し、ワールドのsource blockを消費しない。溶岩や他MOD流体にも適用され得る。

## ST-008：Grinderの開始条件・コスト・初期充電

## ST-009：かまど隠し流体の撤去ライフサイクル

- **優先度／根拠**：P1、S-J（座標別SavedData）・S-P・H（撤去時残存）。
- **静的事実**：`FurnaceCondensedSlimeStorage` は `BlockPos.asLong()` をキーとする量のMapを持つ。BlockEntity本体のNBTとは別で、容量8,000 mB。
- **懸念**：撤去時の適切な削除／移管経路がなければ、同座標の新しいかまどが以前の量を引き継ぐ。保存データの残存・移動MODとの組合せも調査対象。
- **0.3.0**：未修正。
- **再現**：部分充填→破壊→同座標再設置、別座標設置、別ブロック置換、再起動、別ディメンション同座標、チャンクアンロードを試す。アンロードを破壊とみなして掃除しない。
- **合格条件**：実際の撤去と単なるロード状態変化を区別し、流体の復活・二重所有・意図しない消去がない。回収時の保持方針をADRに記録する。

## ST-022：かまど端数変換で素材を消費せず流体が増える可能性【追加仮説】

- **優先度／根拠**：P0の再現調査、S-J・I。**実ゲーム未再現。0.3.0のモデル試験にもない。**
- **確認した処理**：`FurnaceCondensedSlimeStorage.insert` は `min(8000 - stored, requested)` mBをそのまま保存へ加える。一方、`FurnaceCondensedSlimeCompat.processFurnaceOutput` は返った挿入量を整数で1,000除算した個数だけDried Slimeから減らす。Storageの `extract` は1,000の倍数に限定されていない。
- **推論**：保存量7,500 mB、出力Dried Slime 1個、空バケツなしなら、500 mBを挿入して8,000 mBになる一方、`500 / 1000 = 0` で素材が減らない可能性がある。その後に少量抽出すれば同じ素材から繰り返せる懸念がある。
- **作業**：実際の配管で7,500 mB等の端数へ到達できるか、同tickの再処理と出力更新を含めて最小再現する。7,000/7,500/7,999/8,000 mB、素材1/2/64個、バケツ0/1/2個、抽出あり／なしを試す。
- **修正候補**：空きが1,000 mB以上ある個数分だけ原子的に変換する、または端数の未完了変換を明示保存する。元の比率1個→1,000 mBを維持する。
- **合格条件**：初期流体、消費素材由来の流体、バケツ化、抽出量、最終保存量の収支が一致する。再起動・満杯・部分抽出で素材の二重使用がない。

## PATCH-001：参考パッチ自身の問題・レビュー対象

- **優先度／根拠**：P0/P1、S-P。元MODの不具合とは分けて扱う。
- **本物のMixin適用**：コンストラクタへのModifyConstant、複数対象のrequire/allow、Accessor、ordinal 0/3等は独自Weaverだけで確認されている。実適用で検証する。
- **サーバー側分離**：JEIはクライアント任意依存の宣言だが、参考build.gradleは共通runtimeOnlyにJEIを含む。JEIなし専用サーバーを本当に起動する構成にする。
- **保留時表示**：Tankが0表示だと利用者が空と誤認する。実残量を維持したまま、保留の理由・状態を確認できる設計にする。
- **設定説明**：`blockNonWaterWorldSources` の日本語説明「溶岩・水以外」は曖昧。実際のコードは水以外すべて、溶岩を含めて拒否。コード・設定例・日英説明を揃える。
- **保存スキーマ**：参考PumpSafetyはスキーマ番号を保存する。将来のスキーマ値、既存キーとの競合、保留状態の再保存を明示的に扱う。
- **性能とログ**：安全性確認はアクセスごとに探索する。上限設定やログ抑制を含め、パッチが追加する負荷も計測する。
- **適用対象**：ビルド時の元JARハッシュ検査に対して、実行時はバージョンと注入対象数のみ。実行時ハッシュ／構造指紋の採用可否を検討し、同名・同版の別JARに対する保証範囲を明示する。
- **クライアント設定**：サーバー設定が実効値。表示がローカル設定だけで挙動を断定しないようにする。
- **ロールバック**：パッチが書き加えた保留データを旧版が理解するとは限らない。JARだけを戻す手順ではなく、導入前のワールド・設定・MOD構成をセットで戻す手順を整える。
